1. Singleton Pattern

Übung: Warum ist diese Klasse problematisch?

class DatabaseConfig {
    private String url = "jdbc:h2:./db/school";
    private String user = "sa";
    private String password = "";

    public String getUrl() {
        return url;
    }

    public String getUser() {
        return user;
    }

    public String getPassword() {
        return password;
    }
}

Überlege: Was passiert, wenn im Programm mehrere Objekte von DatabaseConfig erzeugt werden?

Lösung

Ohne Singleton könnten mehrere unterschiedliche Konfigurationsobjekte entstehen. Dadurch könnten verschiedene Teile des Programms mit unterschiedlichen Datenbankeinstellungen arbeiten. 

DatabaseConfig config1 = new DatabaseConfig();
      DatabaseConfig config2 = new DatabaseConfig();
      
      config1.setUrl("jdbc:h2:./db1");
      config2.setUrl("jdbc:h2:./db2");

Das Singleton Pattern verhindert das, indem nur eine einzige Instanz der Klasse existiert. 

class DatabaseConfig {
    private static final DatabaseConfig INSTANCE = new DatabaseConfig();

    private String url = "jdbc:h2:./db/school";
    private String user = "sa";
    private String password = "";

    private DatabaseConfig() {
    }

    public static DatabaseConfig getInstance() {
        return INSTANCE;
    }

    public String getUrl() {
        return url;
    }

    public String getUser() {
        return user;
    }

    public String getPassword() {
        return password;
    }
}

2. Simple Factory

Übung: Warum ist die Objekterzeugung hier ungünstig?

class Main {
    public static void main(String[] args) {
        String type = "teacher";

        if (type.equals("teacher")) {
            User user = new Teacher();
            user.printRole();
        } else if (type.equals("student")) {
            User user = new Student();
            user.printRole();
        }
    }
}

Die Entscheidung, welches Objekt erzeugt wird, steht direkt in der Programmlogik. Diese Logik kann ausgelagert werden.

Lösung

Eine Simple Factory übernimmt die Objekterzeugung an einer zentralen Stelle. 

interface User {
    void printRole();
}

class Teacher implements User {
    public void printRole() {
        System.out.println("Ich bin Lehrer.");
    }
}

class Student implements User {
    public void printRole() {
        System.out.println("Ich bin Schüler.");
    }
}

class UserFactory {
    public static User createUser(String type) {
        if (type.equals("teacher")) {
            return new Teacher();
        }

        if (type.equals("student")) {
            return new Student();
        }

        throw new IllegalArgumentException("Unbekannter Typ: " + type);
    }
}

class Main {
    public static void main(String[] args) {
        User user = UserFactory.createUser("teacher");
        user.printRole();
    }
}

3. Factory Method Pattern

Übung: Wie kann man vermeiden, dass diese Klasse direkt konkrete Repositorys erzeugt?

class Application {
    public void run() {
        StudentRepository repository = new H2StudentRepository();
        repository.findAll();
    }
}

Die Klasse Application hängt direkt von H2StudentRepository ab. Eine Unterklasse könnte entscheiden, welches Repository erzeugt wird.

Lösung

Beim Factory Method Pattern definiert eine Oberklasse eine Methode zur Objekterzeugung. Unterklassen entscheiden, welches konkrete Objekt erzeugt wird. 

interface StudentRepository {
    void findAll();
}

class H2StudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Lese Schüler aus H2-Datenbank.");
    }
}

class MySqlStudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Lese Schüler aus MySQL-Datenbank.");
    }
}

abstract class Application {
    public void run() {
        StudentRepository repository = createRepository();
        repository.findAll();
    }

    protected abstract StudentRepository createRepository();
}

class H2Application extends Application {
    protected StudentRepository createRepository() {
        return new H2StudentRepository();
    }
}

class MySqlApplication extends Application {
    protected StudentRepository createRepository() {
        return new MySqlStudentRepository();
    }
}

4. Abstract Factory Pattern

Übung: Warum wird es unübersichtlich, wenn mehrere passende Repositorys erzeugt werden müssen?

class Main {
    public static void main(String[] args) {
        StudentRepository studentRepository = new H2StudentRepository();
        TeacherRepository teacherRepository = new H2TeacherRepository();

        studentRepository.findAll();
        teacherRepository.findAll();
    }
}

Wenn man von H2 auf MySQL wechseln möchte, müssen mehrere Stellen angepasst werden. Eine Factory kann zusammengehörige Objekte erzeugen.

Lösung

Eine Abstract Factory erzeugt zusammengehörige Objektfamilien, zum Beispiel alle Repositorys für H2 oder alle Repositorys für MySQL. 

interface StudentRepository {
    void findAll();
}

interface TeacherRepository {
    void findAll();
}

class H2StudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Schüler aus H2 lesen.");
    }
}

class H2TeacherRepository implements TeacherRepository {
    public void findAll() {
        System.out.println("Lehrer aus H2 lesen.");
    }
}

class MySqlStudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Schüler aus MySQL lesen.");
    }
}

class MySqlTeacherRepository implements TeacherRepository {
    public void findAll() {
        System.out.println("Lehrer aus MySQL lesen.");
    }
}

interface RepositoryFactory {
    StudentRepository createStudentRepository();
    TeacherRepository createTeacherRepository();
}

class H2RepositoryFactory implements RepositoryFactory {
    public StudentRepository createStudentRepository() {
        return new H2StudentRepository();
    }

    public TeacherRepository createTeacherRepository() {
        return new H2TeacherRepository();
    }
}

class MySqlRepositoryFactory implements RepositoryFactory {
    public StudentRepository createStudentRepository() {
        return new MySqlStudentRepository();
    }

    public TeacherRepository createTeacherRepository() {
        return new MySqlTeacherRepository();
    }
}

5. Adapter Pattern

Übung: Wie kann diese alte Klasse weiterverwendet werden, obwohl sie nicht zum neuen Interface passt?

class OldCsvStudentReader {
    public String[] readStudentsFromCsv() {
        return new String[] { "Max", "Anna", "Sara" };
    }
}

interface StudentReader {
    List<String> readStudents();
}

Die alte Klasse liefert ein Array zurück. Das neue Interface erwartet aber eine List<String>.

Lösung

Ein Adapter übersetzt zwischen einer bestehenden Klasse und einem erwarteten Interface. Die alte Klasse muss dadurch nicht verändert werden. 

import java.util.Arrays;
import java.util.List;

class OldCsvStudentReader {
    public String[] readStudentsFromCsv() {
        return new String[] { "Max", "Anna", "Sara" };
    }
}

interface StudentReader {
    List<String> readStudents();
}

class CsvStudentReaderAdapter implements StudentReader {
    private OldCsvStudentReader oldReader;

    public CsvStudentReaderAdapter(OldCsvStudentReader oldReader) {
        this.oldReader = oldReader;
    }

    public List<String> readStudents() {
        return Arrays.asList(oldReader.readStudentsFromCsv());
    }
}

class Main {
    public static void main(String[] args) {
        OldCsvStudentReader oldReader = new OldCsvStudentReader();
        StudentReader reader = new CsvStudentReaderAdapter(oldReader);

        System.out.println(reader.readStudents());
    }
}
