Ziel

Design Patterns sind bewährte Lösungsansätze für typische Probleme in der Softwareentwicklung. Auf dieser Seite lernst du wichtige Patterns anhand einfacher Java-Beispiele kennen.

Die Beispiele sind bewusst einfach gehalten. Einige Beispiele verwenden Tiere oder grafische Oberflächen, andere orientieren sich am JDBC-Umfeld mit Repositorys, Datenbanken und Konfigurationen.

1. Singleton Pattern

Problem:
Eine zentrale Konfiguration soll im gesamten Programm nur einmal existieren. 

class DatabaseConfig {
    private String url = "jdbc:h2:./db/school";

    public String getUrl() {
        return url;
    }
}

Überlege, was passiert, wenn mehrere Objekte von DatabaseConfig erzeugt werden.

Erklärung

Ohne Singleton könnten mehrere unterschiedliche Konfigurationsobjekte entstehen. 

DatabaseConfig config1 = new DatabaseConfig();
DatabaseConfig config2 = new DatabaseConfig();

Dadurch könnten verschiedene Teile des Programms mit unterschiedlichen Datenbankeinstellungen arbeiten.

Das Singleton Pattern verhindert das. Die Klasse besitzt eine einzige zentrale Instanz, einen privaten Konstruktor und eine Zugriffsmethode. 

class DatabaseConfig {
    private static final DatabaseConfig INSTANCE = new DatabaseConfig();

    private String url = "jdbc:h2:./db/school";

    private DatabaseConfig() {
    }

    public static DatabaseConfig getInstance() {
        return INSTANCE;
    }

    public String getUrl() {
        return url;
    }
}

Verwendung

DatabaseConfig config = DatabaseConfig.getInstance();

System.out.println(config.getUrl());

Merksatz:
Singleton bedeutet: Von einer Klasse existiert genau eine zentrale Instanz.

2. Simple Factory

Problem:
Die Objekterzeugung steht direkt in der Programmlogik. 

String type = "teacher";

if (type.equals("teacher")) {
    User user = new Teacher();
    user.printRole();
} else if (type.equals("student")) {
    User user = new Student();
    user.printRole();
}

Die Entscheidung, welches Objekt erzeugt wird, kann in eine eigene Factory-Klasse ausgelagert werden.

Erklärung

Eine Simple Factory übernimmt die zentrale Objekterzeugung. Dadurch verschwindet die if-else-Logik aus dem restlichen Programm. 

interface User {
    void printRole();
}

class Teacher implements User {
    public void printRole() {
        System.out.println("Ich bin Lehrer.");
    }
}

class Student implements User {
    public void printRole() {
        System.out.println("Ich bin Schüler.");
    }
}

class UserFactory {
    public static User createUser(String type) {
        if (type.equals("teacher")) {
            return new Teacher();
        }

        if (type.equals("student")) {
            return new Student();
        }

        throw new IllegalArgumentException("Unbekannter Typ: " + type);
    }
}

Verwendung

User user = UserFactory.createUser("teacher");

user.printRole();

Merksatz:
Eine Simple Factory lagert die Objekterzeugung in eine eigene Klasse aus.

3. Factory Method Pattern

Problem:
Eine Oberklasse soll den allgemeinen Ablauf kennen, aber nicht entscheiden, welches konkrete Objekt erzeugt wird. 

Animal animal = new Dog();
animal.makeSound();

Die Erzeugung von Dog oder Cat soll nicht direkt im Hauptprogramm stehen. Eine Unterklasse kann entscheiden, welches Objekt erzeugt wird.

Erklärung

Beim Factory Method Pattern kennt die abstrakte Oberklasse nur die Methode zur Objekterzeugung. Sie weiß aber nicht, welches konkrete Objekt erzeugt wird. 

interface Animal {
    void makeSound();
}

class Dog implements Animal {
    public void makeSound() {
        System.out.println("Wuff");
    }
}

class Cat implements Animal {
    public void makeSound() {
        System.out.println("Miau");
    }
}

abstract class AnimalCreator {
    public abstract Animal createAnimal();
}

class DogCreator extends AnimalCreator {
    public Animal createAnimal() {
        return new Dog();
    }
}

class CatCreator extends AnimalCreator {
    public Animal createAnimal() {
        return new Cat();
    }
}

Verwendung

AnimalCreator creator = new DogCreator();

Animal animal = creator.createAnimal();

animal.makeSound();

Hier entscheidet die Unterklasse DogCreator, dass ein Dog-Objekt erzeugt wird. 

AnimalCreator creator = new CatCreator();

Animal animal = creator.createAnimal();

animal.makeSound();

Wird stattdessen CatCreator verwendet, entsteht ein Cat-Objekt.

Factory Method im Repository-Umfeld

interface StudentRepository {
    void findAll();
}

class H2StudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Lese Schüler aus H2");
    }
}

class MySqlStudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("Lese Schüler aus MySQL");
    }
}

abstract class Application {
    public void run() {
        StudentRepository repository = createRepository();
        repository.findAll();
    }

    protected abstract StudentRepository createRepository();
}

class H2Application extends Application {
    protected StudentRepository createRepository() {
        return new H2StudentRepository();
    }
}

class MySqlApplication extends Application {
    protected StudentRepository createRepository() {
        return new MySqlStudentRepository();
    }
}

Verwendung

Application app = new H2Application();

app.run();

Die Methode run() bleibt gleich. Nur die konkrete Unterklasse entscheidet, welches Repository erzeugt wird.

Merksatz:
Factory Method bedeutet: Die Oberklasse kennt die Erzeugungsmethode, aber die Unterklasse entscheidet über das konkrete Objekt.

4. Abstract Factory Pattern

Problem:
Es sollen mehrere zusammengehörige Objekte erzeugt werden, zum Beispiel alle GUI-Elemente für Windows oder alle GUI-Elemente für macOS. 

Button button = new WindowsButton();
Checkbox checkbox = new WindowsCheckbox();

Wenn mehrere Objekte zusammenpassen müssen, sollte nicht jedes Objekt einzeln im Programm erzeugt werden. Eine Factory kann eine ganze Familie passender Objekte erzeugen.

Erklärung

Eine Abstract Factory erzeugt mehrere zusammengehörige Objekte. Im Beispiel erzeugt eine Factory immer einen passenden Button und eine passende Checkbox. 

interface Button {
    void render();
}

interface Checkbox {
    void render();
}

class WindowsButton implements Button {
    public void render() {
        System.out.println("Windows Button");
    }
}

class WindowsCheckbox implements Checkbox {
    public void render() {
        System.out.println("Windows Checkbox");
    }
}

class MacButton implements Button {
    public void render() {
        System.out.println("Mac Button");
    }
}

class MacCheckbox implements Checkbox {
    public void render() {
        System.out.println("Mac Checkbox");
    }
}

interface GUIFactory {
    Button createButton();

    Checkbox createCheckbox();
}

class WindowsFactory implements GUIFactory {
    public Button createButton() {
        return new WindowsButton();
    }

    public Checkbox createCheckbox() {
        return new WindowsCheckbox();
    }
}

class MacFactory implements GUIFactory {
    public Button createButton() {
        return new MacButton();
    }

    public Checkbox createCheckbox() {
        return new MacCheckbox();
    }
}

Verwendung

GUIFactory factory = new WindowsFactory();

Button button = factory.createButton();
Checkbox checkbox = factory.createCheckbox();

button.render();
checkbox.render();

Soll später macOS verwendet werden, muss nur die Factory ausgetauscht werden: 

GUIFactory factory = new MacFactory();

Der restliche Code bleibt gleich. Button und Checkbox passen weiterhin zusammen.

Abstract Factory im Repository-Umfeld

interface StudentRepository {
    void findAll();
}

interface TeacherRepository {
    void findAll();
}

class H2StudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("H2 Student");
    }
}

class H2TeacherRepository implements TeacherRepository {
    public void findAll() {
        System.out.println("H2 Teacher");
    }
}

class MySqlStudentRepository implements StudentRepository {
    public void findAll() {
        System.out.println("MySQL Student");
    }
}

class MySqlTeacherRepository implements TeacherRepository {
    public void findAll() {
        System.out.println("MySQL Teacher");
    }
}

interface RepositoryFactory {
    StudentRepository createStudentRepository();

    TeacherRepository createTeacherRepository();
}

class H2RepositoryFactory implements RepositoryFactory {
    public StudentRepository createStudentRepository() {
        return new H2StudentRepository();
    }

    public TeacherRepository createTeacherRepository() {
        return new H2TeacherRepository();
    }
}

class MySqlRepositoryFactory implements RepositoryFactory {
    public StudentRepository createStudentRepository() {
        return new MySqlStudentRepository();
    }

    public TeacherRepository createTeacherRepository() {
        return new MySqlTeacherRepository();
    }
}

Rollen im Abstract Factory Pattern

  • Abstract Factory: gemeinsames Factory-Interface, zum Beispiel GUIFactory
  • Concrete Factory: konkrete Factory-Klassen, zum Beispiel WindowsFactory und MacFactory
  • Abstract Products: gemeinsame Produkt-Interfaces, zum Beispiel Button und Checkbox
  • Concrete Products: konkrete Produkte, zum Beispiel WindowsButton und WindowsCheckbox

Merksatz:
Eine Abstract Factory erzeugt mehrere zusammengehörige Objekte.

Wann verwendet man welches Factory Pattern?

Die drei Factory Patterns unterscheiden sich vor allem darin, wer entscheidet und wie viele Objekte erzeugt werden.

Simple Factory

Eine normale Factory-Klasse entscheidet anhand eines Wertes, welches einzelne Objekt erzeugt wird. 

User user = UserFactory.createUser("teacher");

Frage: Welches einzelne Objekt brauche ich?

Factory Method

Eine Oberklasse definiert eine Erzeugungsmethode. Die Unterklasse entscheidet, welches konkrete Objekt erzeugt wird. 

AnimalCreator creator = new DogCreator();

Animal animal = creator.createAnimal();

Frage: Welche Unterklasse soll das Objekt erzeugen?

Abstract Factory

Eine Factory erzeugt mehrere zusammengehörige Objekte, die gemeinsam verwendet werden. 

GUIFactory factory = new WindowsFactory();

Button button = factory.createButton();
Checkbox checkbox = factory.createCheckbox();

Frage: Welche zusammengehörige Objektfamilie brauche ich?

Kurz gesagt

Simple Factory: Eine Klasse entscheidet über ein Objekt.

Factory Method: Eine Unterklasse entscheidet über ein Objekt.

Abstract Factory: Eine Factory entscheidet über mehrere passende Objekte.

5. Adapter Pattern

Problem:
Eine bestehende Klasse soll weiterverwendet werden, passt aber nicht zum erwarteten Interface. 

class OldCsvStudentReader {
    public String[] readStudentsFromCsv() {
        return new String[] { "Max", "Anna", "Sara" };
    }
}

interface StudentReader {
    List<String> readStudents();
}

Die alte Klasse liefert ein Array, das neue Interface erwartet aber eine Liste. Eine Adapter-Klasse kann dazwischen übersetzen.

Erklärung

Der Adapter implementiert das gewünschte Interface. Intern verwendet er aber die alte Klasse und wandelt das Ergebnis passend um. 

import java.util.Arrays;
import java.util.List;

class OldCsvStudentReader {
    public String[] readStudentsFromCsv() {
        return new String[] { "Max", "Anna", "Sara" };
    }
}

interface StudentReader {
    List<String> readStudents();
}

class CsvStudentReaderAdapter implements StudentReader {
    private OldCsvStudentReader oldReader;

    public CsvStudentReaderAdapter(OldCsvStudentReader oldReader) {
        this.oldReader = oldReader;
    }

    public List<String> readStudents() {
        String[] students = oldReader.readStudentsFromCsv();
        return Arrays.asList(students);
    }
}

Verwendung

OldCsvStudentReader oldReader = new OldCsvStudentReader();

StudentReader reader = new CsvStudentReaderAdapter(oldReader);

System.out.println(reader.readStudents());

Rollen im Adapter Pattern

  • Target: gewünschtes Interface, zum Beispiel StudentReader
  • Adaptee: bestehende alte Klasse, zum Beispiel OldCsvStudentReader
  • Adapter: übersetzt zwischen beiden, zum Beispiel CsvStudentReaderAdapter

Die alte Klasse musste nicht verändert werden. Trotzdem kann sie über das neue Interface verwendet werden.

Merksatz:
Ein Adapter macht eine bestehende Klasse kompatibel mit einem erwarteten Interface.
